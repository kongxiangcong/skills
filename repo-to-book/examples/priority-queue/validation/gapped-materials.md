# 第二章研究素材：删除、更新与边界

## 学习目标

分清逻辑成员、物理 entry、对象引用；解释更新为何产生墓碑与新 count；辨认空队列和浮点输入的边界。

## 机制与证据

| 机制 | 必要内容 | 固定源码定位 |
|---|---|---|
| remove 只逻辑删除 | `entry = self._entry_map.pop(task)`；`entry[-1] = _REMOVED` | S01 queueutils.py L140–145 |
| 更新已有 task | 旧项替换为新 entry；具体异常次序未随包保存 | S01 L132–138（仅链接） |
| 只清队首墓碑 | while _pq；读 `_pq[0]`；task is _REMOVED 则 pop/continue；否则 return | S01 L147–156 |
| len 只数有效任务 | `return len(self._entry_map)` | S01 L187–189 |

map 与 backend 指向同一可变列表，所以 remove 修改 task 槽后，后端能看见标记。priority/count 保持不变，不需立即重新排序。更新既不原地改优先级，也不沿用旧 count；它可改变同优先级中的先后位置。没有自动全量 compact。替换 task 槽也释放该 entry 对旧 task 的引用，不能写成旧 task 对象一定被墓碑永久保留。

## 紧接第一章的实际走读

S02 两后端同样得到以下逻辑结果；物理有序展开采用 SortedPriorityQueue：

| 操作 | 有效 / 物理 | 有序 entry 简写 | 结果 |
|---|---:|---|---|
| pop B 后 | 2 / 2 | [-3,2,C],[-1,0,A] | 起点 |
| 更新 A 到 3 | 2 / 3 | [-3,2,C],[-3,3,A],[-1,0,×] | 旧 A 标记，新 A 排在 C 后 |
| remove C | 1 / 3 | [-3,2,×],[-3,3,A],[-1,0,×] | 仍留三个物理 entry |
| peek | 1 / 2 | [-3,3,A],[-1,0,×] | 清 C 墓碑，返回 A |
| pop | 0 / 1 | [-1,0,×] | 返回 A；逻辑已空 |
| pop(None) | 0 / 0 | [] | 清最后墓碑后返回 None |

× 是 `_REMOVED` 的教学简写，不是源码字符串。原始 float 值、实际内存容器次序、命令和输出见 S02。

## 失败与边界表

| 场景 | 结果与确定性 | 依据 |
|---|---|---|
| remove 不存在的 task | KeyError，实际观察 | S01 L144 / S02 |
| 空队列 peek/pop，无 default | IndexError；消息分别 peek/pop on empty queue | S01 L164–185 / S02 |
| 空队列显式 default=None | 返回 None，实际观察 | S01 / S02 |
| task 为 list | TypeError，不可哈希，实际观察 | 字典操作 / S02 |
| 已存在 task 的新 priority 转换失败 | 核心问题：旧任务是否仍可取出？当前包没有对应源代码片段或可复核运行输出，必须有依据才能解释 | S01 / S02 链接待补内容 |
| 自定义 key 返回不可比较项等后端异常 | 不保证回滚，map 在后端插入前写入；静态推断，未注入 | S01 L137–138 |
| 大整数默认转 float | 9007199254740993 转成 9007199254740992.0，再取负；实际观察 | S02 / S04 |
| NaN / inf | float 可接受；代码无有限性检查；不承诺 NaN 有意义的优先顺序 | S01 L105 / S04；未运行 NaN 案例 |

私有 `_REMOVED` 同时是“未提供 default”的哨兵，不作为公开 task/default 使用。用户任务的 hash/equality 应稳定，这是字典机制带来的使用约束；未测试恶意对象。没有锁或等待协议的实现不应画成线程安全生产者消费者队列。

## 性能与资源界限

令 N=物理 entry 数、L=有效任务数。普通 hash/equality 下 remove 是平均 O(1) 字典操作加槽改写。HeapPriorityQueue 的 add 后端为 O(log N)；peek/pop 可能先清 c 个墓碑，单次公开调用不能只写 O(1)/O(log L)。持续更新而不访问队首会让物理 N 增长。SortedPriorityQueue 默认 BarrelList 不能直接套用内建 list 的复杂度；精确渐近分析与吞吐测试在范围外。
