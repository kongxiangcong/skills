# 第一章　谁先离开队列？ {#lifecycle}

把三件待办交给一个队列：A 的优先级是 1，B 和 C 都是 3，并按 A、B、C 的次序加入。假如按到达时间处理，A 会先出来；假如优先级更重要，就要先处理 B 或 C。可是 B 和 C 同级，谁又应当先出来？

本章用这个小问题拆开 boltons 优先队列的接口和内部条目。读完后，你应当能把一次 `add` 写成一个可比较的条目，并解释为什么看队首和取走队首是两件事。

**本书的证据范围。** 研究材料标注的项目版本是 `d31d821d56c8f7756af9c30a864077f2e5855321`，读取日期为 2026-10-27。本版携带了研究者整理的代码短摘录、走读表和图片，但没有携带完整源码快照、探测脚本和原始运行输出。以下项目行为来自这些材料；“材料报告”不能理解为本次写作重新运行或独立核验。来源附录保留了原始登记，其中关于随包文件的描述与实际内容不一致，须结合这一说明阅读。[S01](../sources.md#s01)、[S02](../sources.md#s02) 是来源定位，并非可以离线打开的完整证据。

## 从优先选择到可以比较的条目 {#entry}

先看一张概念插画：它只用“先挑一张任务卡”的动作帮助理解优先选择。不要从人物、卡片位置或数量推导排序算法。

![图 1-1　优先选择的概念隐喻。插画不表示真实容器布局、线程、容量或精确执行顺序。](../chapters/01-lifecycle/assets/fig-01-02.png)

程序需要把“更紧急”变成明确的比较关系。材料给出的默认转换是：

```python
_default_priority_key = staticmethod(lambda p: -float(p or 0))
```

先把优先级转成浮点数，再取负号，因而 3 变成 −3.0，1 变成 −1.0。后端先取较小的比较值时，原先较大的优先级就会先出现。这里最好区分两个词：**输入优先级**是调用者传入的数，**有效优先级**是转换后真正参与排序的值。把二者混在一起，就容易把方向说反。[S01](../sources.md#s01)

还有两个细节。`p or 0` 会先把 `None` 和其他假值归为零；它不是只处理 `None`。其次，允许自定义 `priority_key`，但自定义函数输出的是比较值。例如材料中的 `lambda p: p` 不再取负号，在输出具有正常可排序语义时，较小输出先出。不能把默认规则“输入数值越大越靠前”推广到任意自定义函数。

只保存有效优先级和任务还不够：B 与 C 的有效优先级一样。材料中的条目由三个槽组成：

```python
entry = [priority, count, task]
```

`count` 是递增序号。先比较有效优先级，同级时再比较序号，因此 B 的序号 1 小于 C 的序号 2，B 先出。序号还把正常同级比较挡在任务对象之前：即使任务本身没有定义大小关系，也通常不必比较任务对象。这里的前提是优先级能够正常排序；NaN 等边界不能靠“有序号”就自动解决。

## 跟着 A、B、C 走一遍 {#walkthrough}

下表把材料中的成功路径重新展开。为便于看清顺序，展示的是 `SortedPriorityQueue` 的有序条目，省略浮点数的小数部分。方括号依次表示有效优先级、序号、任务。它是教学走读，原始运行记录未随当前包提供。[S02](../sources.md#s02)

| 调用 | 队列中的条目 | 返回任务 | 有效任务数 |
|---|---|---|---:|
| `add('A', 1)` | `[-1,0,A]` | — | 1 |
| `add('B', 3)` | `[-3,1,B]`，`[-1,0,A]` | — | 2 |
| `add('C', 3)` | `[-3,1,B]`，`[-3,2,C]`，`[-1,0,A]` | — | 3 |
| `peek()` | 三条均保留 | B | 3 |
| `pop()` | `[-3,2,C]`，`[-1,0,A]` | B | 2 |

第三行是关键。B、C 的第一槽相同，所以第二槽决定顺序；A 的第一槽较大，因此排在两者之后。`peek()` 回答“下一件是什么”，保留有效任务；`pop()` 则同时取走任务。二者返回的是 B 这个任务，不是整个三槽条目。表中的“—”表示没有返回任务；材料记录的 `add` 返回值为 `None`。

不过，不能由这张表断言 `peek()` 从不改变内部结构。本例没有失效条目，才恰好保持不变。第二章会看到，访问队首之前的清理可以改变物理容器，而不删除有效任务。

## 一次加入，留下两个入口 {#two-views}

接下来的流程图追踪成功加入一个任务，再选择查看或弹出队首的过程。先沿竖线看新条目如何建立，再看下面两个后续调用；分叉不是说 `add` 会自动调用 `peek` 或 `pop`。

![图 1-2　成功路径中的条目创建与队首访问。图中的转换、删除旧任务只表示成功路径涉及的动作，不提供失败时二者的先后及回滚保证；首次加入的走读不依赖这项未决问题。](../chapters/01-lifecycle/assets/fig-01-01.svg)

材料中的初始化建立三种状态：后端 `_pq` 保存可排序的条目；字典 `_entry_map` 从任务找到条目；计数器 `_counter` 提供新序号。创建条目后，材料给出了这两句：

```python
_entry_map[task] = entry
_push_entry(self._pq, entry)
```

同一个可变列表被字典和后端共同引用，而不是制作两个内容相同的副本。后端适合回答“谁在队首”，字典适合回答“这个任务当前对应哪条记录”。这种双入口设计为下一章的删除提供了条件。[S01](../sources.md#s01)

它也带来使用约束：任务要可哈希，成员身份遵从字典的哈希与相等判断，不只看是不是同一个对象。把一个普通列表当任务会遇到不可哈希的问题。长期放在字典中的任务也需要稳定的哈希与相等语义，不能任意改变其成员判断依据。

流程图没有画异常分支。尤其是“更新已有任务时，新优先级转换失败，旧任务还在不在”这一问题，当前包不能作答。图中“转换优先级；同任务先 remove”的文字不能代替具体语句次序；我们将在第二章保留这个缺口，而不从成功流程推导事务保证。

## 相同接口，不同后端 {#backends}

默认名字容易让人先入为主：看到 `PriorityQueue` 就以为它一定是堆。材料明确给出的别名却是：

```python
PriorityQueue = SortedPriorityQueue
```

因此，讨论默认类型时应先指向排序队列。两种后端共用条目模型和公开操作，但内部维护顺序的方式不同。[S01](../sources.md#s01)

| 类型 | 材料给出的后端操作 | 阅读时要守住的边界 |
|---|---|---|
| `HeapPriorityQueue` | `heappush` / `heappop` | 堆保证队首选择，不意味着内部数组整体有序 |
| `SortedPriorityQueue` | `BList`、`insort` / `pop(0)` | 正常安装时 `BList` 指 `BarrelList`；导入失败才回退内建列表 |
| `PriorityQueue` | 上一行的别名 | 不能根据常见堆队列配方猜测默认后端 |

这也是前面的表必须注明后端的原因：把排序队列的整体有序展示画成堆数组，会让正确的返回顺序变成错误的内部布局说明。材料没有性能基准，也不包含 `BarrelList` 全结构分析，因而本书不宣布哪种后端在真实负载中更快。

此刻可以检验自己的理解：如果再加入同级任务 D，它为什么不会越过仍在队列中的 C？答案应当同时提到相同的有效优先级和更大的新序号。如果只能回答“先进先出”，就遗漏了跨优先级时 A 已经让位给 B、C 的条件。

一次 `pop` 之后，B 离开，C 和 A 留下。接下来把 A 的优先级改成 3，再删掉 C。乍看队列只剩 A，可是物理容器可能仍有三条记录。理解这个差别，才能理解删除与更新的成本。
