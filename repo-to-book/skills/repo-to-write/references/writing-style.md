# 写作风格约定（简版）

本文件单独维护技术书的基础文风约束。若专题目录下的 `outline.md` 在「全书约定」中有更具体的风格或例子规则，优先服从 `outline.md`。

## 1. 标题直接陈述技术对象，不用引导式问题

- 章标题与各级小节标题直接写明模块、机制、数据结构或处理阶段，不写设问句、悬念句或口号式标题。
- 正例：`第 2 章 · 算子融合与输出轴序`、`描述符格式与字段对齐`、`越界输入的编译期拦截`。
- 反例：`为什么系统要分成这几层？`、`正常路径之外接口还承诺什么？`、`如何让算子跑得更快？`。

## 2. 保留必要英文术语，不要机械翻译

- 架构、编译器、协议与代码中的通用英文术语、结构名、IR/Pass 名、硬件单元与字段名直接保留英文，或首次出现时用“中文（英文）”交代后沿用自然写法。
- 直接保留的常见词示例：`descriptor`、`tile`、`stride`、`pad`、`axis order`、`pass`、`pipeline`、`buffer`、`tensor`、`in-place`、`fallback`、`lowering`、`dispatch`。
- 不要把行业内习惯直接说英文的术语机械硬译成生僻中文（例如不要把 `tile` 硬译成“瓦片”，不要把 `pass` 硬译成“遍”，不要把 `lowering` 硬译成“降级”）。中英文之间保持自然阅读节奏，不强行追求“全中文纯洁性”。

## 3. 开门见山，去 ChatGPT 腔

- **删掉公关式开场与总结升华**：章首、节首直接进入技术对象、输入条件或硬件/系统约束。不写“在现代计算系统中，X 扮演着至关重要的角色”、“通过上述精妙设计，系统实现了性能与灵活性的完美平衡”、“总而言之”、“值得注意的是”等套话。
- **不造抽象包装词**：用具体的位宽、数据结构、控制流和状态变化说话，不脱离代码自造“双层解耦范式”、“多维协同机制”、“动态赋能架构”等空泛名词。
- **按因果链行文，不拼贴笔记**：把材料中的事实串成“前置约束 → 具体设计/格式 → 状态变化 → 边界代价”的连贯段落。不要把 `materials.md` 里的要点机械改成“首先…其次…最后…”或满篇单句加粗列表。
- **图表承接并列信息**：3 个以上并列字段、位宽定义、模式对比直接放进表格或配图；正文只写读者需要从图表中看出的规律、约束或反例，不把表格每一行再用文字复述一遍。

## 4. 顺从 `outline.md` 的叙述顺序与首章校准

- 例子出现的位置（如“先解释完描述符格式再给具体例子”）、概念归属（如“输出轴序作为算子融合下的一种实现”）严格遵守 `outline.md` 的约定。
- 当用户希望先看文风效果时，先写完第一章（或指定小节）的 `manuscript.md` 供用户审阅；用户顺手改定的句式偏好直接沉淀回 `outline.md` 的「全书约定」，后续章节一致沿用。
